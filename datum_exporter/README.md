# Datum exporter helpers

`datum_exporter` manages Vector configuration, binary installation and systemd services.
Install from this checkout with `uv tool install '.[exporter]'` (or `pip install '.[exporter]'`).
The YAML dependency is optional; `datum_client` remains standard-library-only.
The existing `datum_client.vector.install()` API is unchanged.

## Non-root installation

On Linux x86_64 or ARM64, run as the user who can read the logs:

```sh
datum-exporter install-binary
datum-exporter init --endpoint https://datum.example.com --token-file /path/to/token
datum-exporter add-file app '/var/log/my-app/*.log' --product my-app --validate
datum-exporter service install
datum-exporter service status
```

The binary is installed at `~/.local/bin/vector`. Configuration, private credentials and
checkpoints live under `$XDG_CONFIG_HOME/datum-exporter` (default `~/.config/datum-exporter`).
The unit goes into `$XDG_CONFIG_HOME/systemd/user`. No package manager or sudo is used.
The installer pins Vector 0.59.0 and checks its archive against bundled SHA-256 hashes of the
[official release archives](https://vector.dev/docs/setup/installation/manual/from-archives/).
Only the regular binary file is copied from the archive, atomically replacing the old binary.
Restart the service explicitly after replacing its binary.

User services require a running user systemd manager. To keep one running after logout and
start it at boot, an administrator may need to run `loginctl enable-linger USER` once. The
helper does not change login policy. Logs must be readable and checkpoint directories writable
by the service user. Run user commands in that user's login session, not via `sudo`.

`--token-file -` reads the token from stdin. To rotate credentials, repeat `init`, then run
`datum-exporter service restart`. Existing application configuration and checkpoints are kept.

## System-wide installation

Install the Python package/CLI for root, then run the same sequence as root with
`datum-exporter --scope system ...`. This installs the binary at `/usr/local/bin/vector`,
configuration and checkpoints at `/etc/datum-exporter`, and the unit at
`/etc/systemd/system/datum-exporter.service`. The system service runs as root.
The default remains user scope even when invoked by root; system scope must be explicit.

Global options precede the command. Use `--directory /path/to/config` and
`--binary /absolute/path/to/vector` to override locations. Each instance needs its own
configuration directory and `service --name NAME` (without `.service`).

Both scopes support `service install`, `start`, `restart`, `stop`, `status`, and `remove`.
Installation enables the service and restarts it, including on repeated installation.
Use `service install --no-start` to enable it without changing its running state.
Start, restart and install validate configuration first. Validation resolves secrets but
skips environment checks and network health checks; it does not prove ingestion works.
Removal stops and disables the service, deletes only its managed unit, and retains the binary,
config, secrets and checkpoints. Unrelated unit files are refused. systemctl failures are
reported; an activation failure leaves the installed unit/config available for diagnosis.

## Edit configuration

```sh
datum-exporter set sources app read_from --value beginning --validate
datum-exporter set sources app include --value '["/var/log/my-app/*.log", "/srv/app/*.log"]'
datum-exporter component sources app --file source-update.yaml --validate
datum-exporter remove sources app exclude --validate
datum-exporter validate
datum-exporter service restart
```

`component` adds or recursively merges a source, transform or sink mapping; `--replace`
replaces that component instead. Lists and scalars replace existing values. `set` takes
individual mapping keys followed by a YAML/JSON value, so keys containing dots need no escaping.
`remove` deletes a key and fails if it is absent. Removing a source does not automatically
remove transforms that reference it. `--validate` checks the proposed config with Vector before
replacing the file; invalid edits leave the previous file intact. Omit validation while building
an incomplete pipeline and validate once it is complete. Edits never restart a service implicitly.

Edits preserve unrelated configuration values, but PyYAML rewrites formatting and comments.
They operate on `app.yaml`; the shared `datum.yaml` is regenerated by `init` and should not be
edited. Custom transforms that feed Datum must end in `_to_datum`. Names `datum` and
`datum_line` are reserved. See the [pipeline contract](../datum_client/vector/README.md) for
normalization, batching and delivery behavior.

## Python API

```python
from pathlib import Path
from datum_exporter import Config, Service, install, install_binary

root = Path.home() / ".config/my-app/vector"
binary = install_binary()  # Linux, user-local by default
install(root, endpoint="https://datum.example.com", token=token)
(root / "data").mkdir(exist_ok=True)
config = Config(root / "app.yaml")
config.set(["data_dir"], str(root / "data"))
config.file_source("app", ["/var/log/my-app/*.log"], product="my-app")
config.component("sources", "app", {"read_from": "beginning"})
config.save(binary=binary)
service = Service(root, binary=binary, name="my-app-logs")
service.install()
```

`Config.data` exposes the loaded mapping. `set`, `remove`, `component` and `file_source`
return the config for chaining; `save` returns its path. Config files and secrets are written
atomically per file with mode 0600. Multiple-file installation and activation are not one
transaction. Serialize edits, credential changes and service lifecycle calls in your application;
there is no cross-process lock or automatic rollback. The helper does not mint or renew tokens.

## Verification

Run `uv run pytest tests/test_exporter.py` with Vector 0.59.0 on `PATH` for config, installer,
CLI and service unit tests. Set `VECTOR_REQUIRE_TESTS=1` to require the real Vector checks.
For live lifecycle verification on a disposable Linux systemd host, run
`python tests/exporter/systemd_smoke.py --scope user` as a login user and the same script
with `--scope system` as root. It downloads the pinned binary into a temporary directory,
uses `datum-exporter-proof.service`, delivers logs to a local HTTP receiver, rotates credentials,
checks restart/checkpoint behavior, and removes its unit. Do not run it concurrently with
another proof in the same scope. The receiver verifies transport; the repository's existing
Vector tests separately verify the Datum ingestion schema.
